Plan Mode：编码 Agent 的标准流程

execution（可并行子代理）

Cursor、Claude Code、Codex 都引入了 Plan Mode：写持久计划 → 人验证 → 执行。可能带来的收益：更多算力、更好上下文、外部工件、分解、或人工批准本身。

定义 1

显式表示未来意图

计划是「Agent 将尝试的动作或子目标 + 顺序与依赖」的显式表示。

定义 2

针对本任务

与技能相对：技能提供跨任务可复用指导；计划可以比技能更具体。

定义 3

是提案不是保证

可被用户、另一个模型、环境交互检查与修订。

🥊 泰森法则
"Everybody has a plan until they get punched in the mouth." —— Mike Tyson。计划必须为「挨打」预留重规划通道。

04

行动前分解：从 CoT 到模块化

"Weeks of programming can save you hours of planning." —— programmer proverb（反讽：编程数周可能只能省几小时的规划）

Chain-of-thought 就是计划

CoT 直接解
Q: [problem] A: Let's think step by step.

Kojima et al., NeurIPS 2022

Plan-and-Solve
Q: [problem] A: Let's first understand the problem and devise a plan to solve it. Then, let's carry out the plan step by step.

Wang et al., ACL 2023

共同点：计划与答案在同一次模型生成中产生，没有东西显式检查计划。但 CoT 可被训练以提高答对概率（STaR；DeepSeek-R1）。

Least-to-Most：先拆后解

Stage 1 写子问题 → Stage 2 顺序回答并前传答案
Stage 1
问题 → 子问题列表
→
Stage 2
子问题 1 → 答案 → 子问题 2 → 答案 …
发现

模型答子问题更准

复杂问题答不动，但拆开的小问题答得不错。

上下文

每个子问题需要更少上下文

注意力聚焦，减少无关信息干扰。

趋势

提升随问题长度增长

问题越长受益越大。Zhou et al., ICLR 2023

分解带来模块化（Decomposed Prompting）

分解器 + 专门 handler "What awards have movies produced by people born in 1910 won?" → "Who were born in the year 1910?" # simple QA handler → "For which movies was #1 the producer?" # position QA handler → … Khot et al., ICLR 2023

模块化允许独立改进每个 handler：为它加 in-context 演示，或单独训练。程序化/结构化控制先行于此——RAO、RLM、MACU 都在此路线上。

05

推理 vs 行动 vs 经典规划

"We'll burn that bridge when we come to it." —— 过桥再看，计划要跟着现实走。
CoT 推理步骤
  • 只改变文本
  • 可以靠「再多写点」撤销
  • 每个中间步可见
  • 计划有用 ⇔ 模型能更好地条件化于它
世界中的行动
  • 改变Agent 下一步遇到的状态
  • 可能揭示信息
  • 可能失败
  • 可能不可逆：submit、send

行动意味着计划必须处理：可行性、后果、信息获取、恢复。

经典规划：STRIPS

积木世界 · 谓词状态 + 前提/效果 # 状态 = 谓词集合 on-table(x) · on(x, y) · clear(x) · holding(x) · hand-empty # 动作 = 前提 → 效果 pick-up(x): on-table(x) ∧ clear(x) ∧ hand-empty → holding(x) ∧ ¬on-table(x) ∧ ¬hand-empty # 目标：on(orange, blue) → 搜索出合法动作序列 unstack(blue, orange) → put-down(blue) → pick-up(orange) → stack(orange, blue) STRIPS · Fikes & Nilsson, 1971 · PlanBench

变的不是搜索，是难点

💡 有了 LLM，一切都变隐式了
对 LLM Agent：写一个像样的计划变容易了，判断自己的世界模型是否正确变难了。所以 Agent 设计少用深层搜索，更多是检查世界——观察、验证、从错误中恢复。但「搜索」「动作适用性」仍然是有的概念。
06

计划的表示方式

正式计划（可检查）⇄ 程序（中间）⇄ 语言计划（通用）
Formal

正式计划

可检查正确性——但表示能力受限。

Program

程序

用代码 LLM 写调用感知/控制 API 的代码；可运行、可检查，但受 API 与程序结构限制。Code as Policies · ProgPrompt · Binder（2023 系列）

Language

语言计划

灵活通用——但无通用验证器（开放问题）。

注意：程序里的 API本身可以调用 LLM 或另一个神经模型——程序与语言并非互斥。

何时重规划

三种承诺程度

风格决策时点行为
Developer-defined workflow执行前开发指定流程：检查固定供应商列表。Agentless（下一讲）
Plan-then-execute执行前模型计划查哪些供应商，执行前承诺。
Adaptive执行中四家失败后，执行反馈引导模型去搜第五家。RAO · MACU
开发者固定流程示例 for v in VENDORS: # 固定列表 specs[v] = read_specs(v) # 模型调用 ok = [v for v in specs if fits(v)] requisition(cheapest(ok))

08

分离 Planner 与 Executor

UGround

语言规划 + 像素执行

GPT-4o 视觉接地强，但生成像素级动作很差：用语言描述下一步。独立训练的 7B executor 把描述映射到屏幕坐标。Gou et al., ICLR 2025

Plan-and-Act

用老师轨迹训练

老师模型分割并标注成功轨迹成计划 → 分别微调 planner 与 executor 模型。Erdogan et al., ICML 2025

分离的模块可以使用不同的模型和训练数据——各司其职，各自最优化。

⚠️ 小心固定角色与多 Agent

编码任务的角色分解成功有限
角色在任务到达前就被固定：verifier 无法定位故障来复查自己的答案；交接是摘要报告，会丢掉下一个 Agent 需要的上下文。 Don't Sleep on Single-agent Systems · Neubig, 2024 · CodeR

建模「可行动性」：SayCan

用技能价值函数重新打分计划的子目标 # 经典规划：动作有前提条件 → 学一个每个技能的价值函数 V(skill) = 预测完成该技能的概率 # 重打分 subtask_score = LLM_plan_prob × V(skill) SayCan · Ahn et al., CoRL 2022

环境反馈触发重规划：LLM-Planner、Inner Monologue、SwiftSage。

思考 vs 行动 vs 查看

Test-Time Interaction

按数列配算力

匹配三种推理方法的计算：更长的 CoT、采样多个候选、或更多与环境交互。「你刚发完成信号，让我们暂停再想想。」——交互扩展能获得环境信息（类似 Reflexion）。Shen et al., NeurIPS 2025

Overthinking

过度思考的代价

三种病态模式：分析瘫痪（analysis paralysis）、失控动作链（rogue action chains）、过早脱离（premature disengagement）。更多过度思考 → 更少问题解决，跨模型类型一致。Cuadron et al., 2025

思考 vs 查看案例：Calibrate-then-Act

隐藏在文件格式里的 12 种组合 # Agent 不知道：每个文件有隐藏格式，三处必须全对才解析 delimiter: , ; \t quote char: " ' header rows to skip: 0 1 # 唯一线索是文件名：sales_fr.tsv → 暗示 tab # CTA 往 prompt 里追加校准信息 Additional context: Format likelihoods: {prior} # 模型读出：分隔符最有可能是 ';'（概率≈0.85），但不确定 → 跑单元测试确认 Ding, Tomlin, Durrett, 2026

长地平线：失败模式与执行水平线

Vending-Bench：一个错误如何滚雪球

任务：长期经营一台自动售货机（定价、下单、补货）。地平线：最多 2,000 条消息 ≈ 2500 万 tokens ≈ 222 个模拟日。后来的动作条件化在 Agent 早期犯的错上。

一次临时错误污染后续每个决策
过早补货
due today ≠ 已送达；环境如实报告：商品不可用
→
错误推断
「现在不可用」→「生意失败」；从不等待履约邮件或复查
→
错误固化
每日费用变成「欺诈」：主题「EMERGENCY: Unauthorized Fees After Business Termination」

Vending-Bench · Backlund & Petersson, 2025：「这只是一个坏计划吗？」——不，是错误没有断点。

执行水平线（Execution horizon）

💡 Sinha et al., 2025
更好的单步准确率延长地平线；而self-conditioning（用自己的输出去条件化）反而可能让后续步骤更不准。更大模型能执行更长任务，但 self-conditioning 更多——强化学习能修复这一点吗？（开放问题）

自适应递归分解与安全边界

RAO：委派是可训练的动作

递归子代理 # Agent 调用 launch_subagent(goal) 运行自身的副本处理子任务，副本还能再派 launch_subagent(goal) # 每个节点按「自身任务 + 子节点成功率」打分 score(node) = task_success(node) + children_success_rate # 只用中等任务训练，它在困难任务上却会委派得更深 RAO · Gandhi et al., 2026 · Recursive Language Models (RLM) · ADaPT

计划作为安全边界

ReAct：每页都能影响下一步
  • 动作直接由页面文本驱动
  • 恶意页面可通过注入改变动作
  • 暴露注入路径
程序计划：接受值，不接受动作
  • 程序固定动作结构
  • 页面只能提供数据值
  • 恶意内容无法加入新动作

Piet et al., 2026：程序化计划把「什么动作」从「哪个值」中分离，天然收紧了注入面。

14

思考题

Q1 · 什么时候别规划？
课程给出了「预先承诺更快更可预测，重规划更适应」。举一个该用固定工作流而非 adaptive 规划的任务，并说明理由。
查看参考思路
例如「批量把 1000 个文件转码并校验哈希」：步骤固定、反馈可预期、无不可逆动作、无跨子任务依赖。此时 adaptive 重规划只会增加成本与抖动（且容易 overthinking）。Agentless 的固定流程正是为此。
Q2 · 分解的失效点
TravelPlanner 展示全局约束在碎片间被违反。如果让你改进，你会选「更长的上下文让全局约束可见」还是「跨子任务校验器」？为什么？
查看参考思路
长上下文成本随轮次二次方增长且已有 25M tokens 级教训；校验器是程序保证——在每次计划修订后跑预算/交通/饮食约束检查，失败即拒绝并附原因，等价于把「全局状态」外化为可执行工件。
Q3 · ReAct 与注入
为什么「程序接受值、不接受动作」能收紧注入面？它牺牲了什么？
查看参考思路
ReAct 中页面文本直接参与动作决策，恶意内容可生成新动作。程序把动作结构固化，页面只能填充数据。牺牲的是灵活性：遇到页面结构变化时程序不再 adaptive——需要重规划机制补位。
Q4 · 委派深度
RAO 只用中等任务训练，为什么在困难任务上却能委派得更深？
查看参考思路
训练让模型学会「何时委派值得」的策略（节点分 = 自身成功 + 孩子成功）。困难任务天然超过单代理能力，策略泛化使得它在更高压力下更频繁调用 launch_subagent——委派是学出来的动作，不是写死的规则。
