03

预训练：数据、清洗与分词

从代码和文本中学习

混合来源

多样化语料

web 文本、技术散文、数学、源码、文档。训练时按域评估 held-out loss。

保留结构

代码的结构即语义

缩进、文件边界、API、文本–代码关系都被保留。

清洗

选与清

按语言/来源过滤（生成垃圾、坏编码、低价值重复）；去重（fork、vendor 库、近似文件、抄袭解）；记录来源（许可证、日期、退出、敏感数据过滤）；防泄漏（按仓库或问题族拆分、评估任务去污染）。

分词

代码感知 subword

字节级 BPE；保留空白（空格/tab/换行带语法与字面内容）；压缩空白运行——把连续空白合并进一个 token，而不是每空格一个 token。

StarCoder2 的空白感知分词 # “·” = 空格, “↵” = 换行, “|” = token 边界 if·ready:↵····return·value↵ if | ·ready | : | ↵··· | ·return | ·value | ↵

规模实证：StarCoderBase

💡 15.5B 参数 · 1T tokens · 80+ 语言
来源覆盖 source / issues / commits / notebooks。大多数语言随训练 token 增多而持续改善——编码能力是「喂」出来的。Li et al., 2023

利用孔右侧的证据 def is_positive(x: int) -> ____: return x > 0 # 主题在孔的右边 → 证据指向 bool def is_positive(x: int) -> bool: return x > 0 InCoder · Fried et al., ICLR 2023

06

评估生成代码

与参考解比较：三种粒度

Exact / BLEU-4

文本相似

精确匹配；token n-gram 重叠 + 长度惩罚。问题是：表达不同、行为等价会被误判。

CodeBLEU

结构相似

AST 与语义结构比较。Ren et al., 2020

CodeBERTScore

表示相似

编码 prompt + 代码，比较上下文 token 向量 → precision/recall → F。Zhou et al., EMNLP 2023

跑起来看行为：functional evaluation

is_positive 的三个变体 # 参考解 return x > 0 # 小改动 → x=0 错误 return x >= 0 # 不同表达式 → 整数上等价 return not (x <= 0) # 测试用例：输入 −1, 0, 1 → 期望 F, F, T → 暴露 x=0 的错误
✓ 执行检查的好处
  • 接受不同的正确实现
  • 通过执行发现语义错误
  • 匹配观察到的行为
✗ 限制
  • 有限测试可能漏掉错误行为
  • 需要可信测试、依赖与隔离执行
  • 要时间与稳定执行环境

Luo et al., 2025 · DeepCoder（Qwen 开源编码模型）

推理的复利：1 + … + n

三种策略，两种错误 # 迭代（太慢） sum(range(n + 1)) # 大 n 太慢 # 配对端点（正确高效） n * (n + 1) // 2 # 推导公式；检查 0, 1 # 凭记忆公式（抄错） n * (n - 1) // 2 # n=1 就已错
💡 实证：RL 提升编码准确率
DeepCoder 在 LiveCodeBench 上：16K → 32K response-token 限制（RL 时 K=1,000 tokens），评估时 64K 更多 token——准确率跨出基线（o3-mini 虚线）。
08

Agentic 编码：localize–edit–verify

单步编码

自包含 prompt → 推理 + 代码 → 评估答案。

Agentic 编码

Issue + 现有文件 → 搜索 → 编辑 → 跑测试 ↺ → Patch + 证据。

核心循环案例：「零变成三」bug

① Localize：先找根因再动手 $ rg 'retries' buggy_config.py return config.get("retries") or 3 # 零是 falsy → 命中默认规则 $ RETRY_MODULE=buggy_config python3 -m unittest test_config.RetryTests.test_zero AssertionError: 3 != 0 # 复现行为：修条件，不是修测试
② Edit：改默认规则 # Before：所有 falsy 值都选中默认值 return config.get("retries") or 3 # After：显式零被保留 value = config.get("retries") return 3 if value is None else value
③ Verify：回归检查 $ python3 -m unittest -v test_config missing → 3 PASS None → 3 PASS zero → 0 PASS positive → 2 PASS Ran 4 tests: OK

验证失败 → 修订假设：零仍变三 → 定位值变化处；默认用例坏了 → 编辑规则再验证。失败是下一步的指南。

备选路线：固定工作流 Agentless——把本地化/编辑/验证写成硬编码阶段（下一讲的「决策时点」对照）。

多步修复 RL 的难点：R2E-Gym

⚠️ 奖励稀疏 + 信用分配
动作（搜索 / 编辑 / 测试 / 结束）是训练目标；工具结果（找到文件、补丁应用、测试输出）只进上下文；终端奖励「修没修好」无法指出是哪个早期决策错了。

注入 bug 造训练数据：SWE-smith

可执行基线的变异验证 # 正常基线：4 个测试全过 Before 4 pass # 变异条件：零变三 → 其测试失败 Mutated 3 pass · 1 fail # 还原：恢复 4 pass Restored 4 pass value = config.get("retries") return 3 if value is None else value # 基线 return 3 if not value else value # 注入的 bug

铁律：变异代码，不碰测试；只有「新测试失败」的变异才保留。

别名陷阱：把引用当拷贝

共享引用 vs 深拷贝 items = [1] alias = items alias.append(2) result = len(items) # 真实执行：items = [1, 2], alias = [1, 2], result = 2 # 错误预测：把 alias 当 copy → result 被猜成 1

预测何时帮助 Agent

⚠️ 决定性的错误
两个候选修复：A 正确、B 错误。模型预测「A 失败、B 通过」→ 选了 B、丢弃 A。对策：跑两个候选来检验模型的判断；比较指标要同时看任务成功率和总延迟 / tokens / 工具调用。

思考题

Q1 · 中训练的比例
Qwen2.5-Coder 的中训练里，100% 代码反而让 MMLU 掉到 23.8。为什么「纯代码」会伤害通用能力？这给「领域专用模型」的训练带来什么启示？
查看参考思路
代码语料的分布与自然语言不同：低熵、结构性强、缺少常识与百科知识。全代码微调会让权重偏移到代码分布，破坏通用表示。启示：领域增强要「掺水」——保留文本与数学，用比例实验而非直觉决定。
Q2 · infilling 的设计
因果掩码 infilling 比「左到右 + 重排」高 14 个点（单行）。这背后是什么机制？
查看参考思路
重排是在生成之后用右文本文本相似度筛选——右文没参与条件化。因果掩码让后缀在生成时就在上下文中，模型直接条件化于右侧证据（如 `return x > 0` 指向 bool）。生成时条件化 > 生成后筛选。
Q3 · 信用分配
R2E-Gym 指出终端奖励无法定位「哪个早期决策错了」。如果让你给多步修复设计更细的奖励信号，你会怎么做？
查看参考思路
在中间动作上注入过程奖励：如「本地化命中」（找到的文件/函数在最终补丁内）给分、每次测试运行后的 fail→pass 变化给增量分、工具使用是否冗余（重复 rg 同目录）扣分。这等价于把 SWE-bench 的 fail→pass 拆细到每个步骤。
Q4 · world model 的边界
「预测代码行为」的模型在什么条件下最值得信任？结合别名陷阱的例子说明。
查看参考思路
引用别名、可变对象、模块副作用这些需要执行才知道的语义，是预测模型的短板。值得信任的条件：任务目标明确且成本模型清楚（预测省下的执行成本 > 预测错误的修复成本）。安全策略：预测只用于剪枝候选，关键路径上始终跑真实验证。
