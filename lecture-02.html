01

工具：定义与收益

工具（Tool）是语言模型调用外部计算机程序的接口。搜索、计算器、浏览器、Python、API——模型只负责「提议」（propose），由外部软件决定是否执行、如何执行。

模型提议 · 外部执行
LLM
生成工具调用声明
→ 提议
外部程序
决定是否/如何执行
→ 结果
模型
继续基于观测推理
Extend 扩展

访问参数之外的世界

获取模型参数中没有的信息或动作：当前时间、私有数据、账户状态、真实世界副作用。模型不知道的，工具去拿。

Facilitate 委托

交给更可靠的执行者

把外部程序做得更好、更可靠、更高效的操作委托出去：精确计算（计算器）、确定性代码（Python）、已授权的应用数据（API）。

⚠️ 何时调用工具
只有在收益超过延迟、成本、失败率和风险时调用工具。每次调用都有真实代价：多一次网络往返、多一次失败机会、多一块攻击面。无脑调用工具是新手常见错误。

03

从「ChatGPT 的组成」看工具设计

课程用一个思想实验开篇：如果从零构建 ChatGPT，需要哪些调用？答案是从「想要的能力」出发，为每种交互定义一个窄接口（narrow interface）：

能力接口类型示例
文本回复finish(text)控制动作finish("阿克拉是加纳首都。")
信息检索search_web(query)工具search_web("site:cmu.edu 今日公告")
代码执行execute_code(code)工具execute_code("sum([18,23,41,54])/4")
图像生成generate_image(query)工具generate_image("图书馆里看书的水彩机器人")
应用功能create_grocery_cart(items)工具create_grocery_cart(["香蕉","牛奶","咖啡"])
💡 关键区分：控制动作 vs 外部工具
finish() 是 harness 控制动作（控制 Agent 循环停止），不是外部程序——它是循环的一部分，不是世界的一部分。设计工具清单时，先把「控制循环的动作」和「改变世界的工具」分开，这是 Agent 框架的架构决策起点。
04

代码作为元工具（CodeAct）

除了把每个能力封装成一个窄函数，还有一种更通用的路径：把代码本身当作工具。一次动作可以包含循环、变量、库调用、多步数据操作。

窄函数工具
  • 单步、类型明确、易于验证
  • 动作空间小，约束精确
  • 适合低频、明确的能力暴露
代码作为工具（CodeAct）
  • 组合控制流 + 库 + 多操作于一步
  • 高表达能力（expressive）
  • 动作空间广 → 难以约束、影响更大
  • 需要沙箱、资源限制、权限、审计日志

CodeAct（Wang et al., ICML 2024）的实证结果：在展示的 8/8 个模型中，代码工具的成功率最高；7/8 的模型用代码工具时轮次最少；扩展到全部 17 个模型，两项统计分别为 12/17。代码工具不是「锦上添花」，而是 Agent 工具调用的最佳实践基线。

⚠️ 代码工具的代价
高功率 = 高责任：能碰文件、网络、进程。必须用沙箱隔离、资源限额、权限控制和审计日志兜底。这正是 Hermes/OpenHands 等框架把 shell 放进 Docker 沙箱的原因。
05

协议细节：从 Schema 到 call ID

工具调用即 token

工具调用就是一次特殊的文本续写：文本续写输出 "The weather is sunny."，工具续写输出一个工具调用块。模型请求动作，harness 执行它。

消息 → 输入序列 → 模型可见

API 的消息（system/user/assistant/tool）通过 chat template 序列化成模型的一个输入序列。角色是 API 层的组织方式，template 决定模型实际看到的字节。

Qwen 输入序列示例（chat template 展开） <|im_start|>system Be concise.<|im_end|> <|im_start|>user Weather in Pittsburgh?<|im_end|> <|im_start|>assistant I need current data.<|im_end|>

统一 Schema，模型专属协议

同一个工具定义（JSON Schema），不同模型用不同的序列化协议表达。这一点对 Agent 框架设计极其重要：工具层必须做模型适配层。课程展示了三种实例：Qwen 用函数+参数标签、Mistral 用控制 token + call ID、DeepSeek 用函数调用标记块（DSML）——一个 Schema，多种模型专属的序列化与解析。

工具定义（统一 Schema）→ API 请求 # 工具定义 { "type": "function", "function": { "name": "get_weather", "parameters": { "type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"] } } } # API 请求：harness 同时发送消息与工具 Schema response = client.chat.completions.create( model=model, messages=messages, tools=[weather_tool], )

06

约束解码：XGrammar 与 PDA

模型可能输出格式错误的工具调用（少了右括号、字段类型错）。约束手段分四层，全部保证「形式」而非「真实」：

约束层含义示例
Syntax合法 JSON{"city": "Pittsburgh"}
Shape期望的字段必须有 arguments 对象
Types字段类型正确city 是 string
Values取值受限units ∈ {C, F}

JSON Schema：描述与校验

JSON Schema 示例 { "type": "object", "properties": { "city": {"type": "string"}, "units": {"enum": ["C", "F"]} }, "required": ["city"], "additionalProperties": false }

XGrammar：在 token 层面做语法遮罩

光校验不够——最好别让模型生成非法 token。XGrammar（Dong et al., MLSys 2025）把 JSON Schema 编译成字节级下推自动机（PDA），在解码的每一步检查候选 token 是否合法，非法 token 直接遮罩。

PDA 的三要素
有限控制

expect value → …

记录当前处于语法规则的哪个位置（期望值、期望分隔符……）。

栈记忆

{ push 对象 … } pop

压栈/弹栈记住任意深度的嵌套：对象里开了数组，弹栈时回到对象规则。

字节级

越过 token 边界

一个 token 可能跨多个语法终结符，所以校验必须发生在 tokenization 之下、按字节推进。

XGrammar 解码 · 4 步遮罩流程 1 · 解析前缀：在已生成的字节上推进持久 PDA 栈 2 · 获取缓存：栈顶节点索引「上下文无关 token」的预计算合法性 3 · 检查少数派：对依赖上下文的候选 token，用完整栈校验 4 · 遮罩继续：合并决策 → 遮罩 logits → 采样 → 更新 PDA 栈
💡 提速来源
XGrammar 的速度来自三件事：缓存（大部分 token 的合法性可预计算复用）、持久栈（支持分支）、CPU/GPU 重叠（掩码计算与推理并行）。实际中语法约束的解码开销可以被压到接近无损。

REST API → OpenAPI → MCP

工具从「进程内函数」到「Agent 可调用的网络服务」，经历了一条经典链路：

三层暴露路径
库函数
进程内 · 不可远程调用
→ FastAPI
REST API
HTTP + 鉴权头
→ 自动生成
OpenAPI 文档
机器可读描述
→ 两种消费
curl 直调
MCP 服务器

第一步：库函数 ≠ 网络服务

进程内库函数 # weather_lib.py — 类型完备的 Python 接口 from typing import Literal from pydantic import BaseModel class Weather(BaseModel): summary: str temperature: float def get_weather(city: str, units: Literal["C", "F"] = "F") -> Weather: return provider.lookup(city, units)

库 API 是类型化的编程接口，但还不是网络服务：网络客户端还需要地址、协议、序列化和鉴权。

第二步：FastAPI 绑定并生成 OpenAPI

REST 端点 + OpenAPI 描述 # api.py — FastAPI 把库函数绑定到 HTTP 端点上 @app.get("/weather", operation_id="get_weather") def weather(city: str, units: Literal["C", "F"] = "F") -> Weather: verify(key) return get_weather(city, units) # OpenAPI 描述（自动生成） { "paths": {"/weather": {"get": { "operationId": "get_weather", "parameters": [ {"name": "city", "in": "query", "required": true, "schema": {"type": "string"}}, {"name": "units", "in": "query", "schema": {"type": "string", "enum": ["C", "F"]}} ], "security": [{"APIKeyHeader": []}] }}}, "components": {"securitySchemes": {"APIKeyHeader": { "type": "apiKey", "in": "header", "name": "X-API-Key"}}} }

编码 Agent 用 curl 直调

curl 调用 REST API curl -sS -G https://weather.example/weather \ --data-urlencode "city=Pittsburgh" \ --data-urlencode "units=F" \ -H "X-API-Key: $WEATHER_API_KEY"
⚠️ 凭据风险
直调 REST 时，拥有 shell 访问权的编码 Agent 可能读到并滥用该密钥。这是 curl 直调的主要安全缺口——MCP 正是为此而生。

MCP：凭据代理与标准发现

MCP（Model Context Protocol）把「AI 宿主」与「工具服务器」解耦：宿主上的客户端通过 stdio（本地）或 HTTP（远程）连接服务器，运行时调用 tools/list / tools/call。

MCP 架构 · 凭据分层
Agent Harness
持有 MCP key
→ MCP 服务器
validate · authorize · dispatch
→ 上游 API
持有 UPSTREAM key

关键设计是凭据代理（credential brokering）：模型看不到任何密钥；MCP 服务器接收一个凭据，使用另一个凭据访问上游。生产环境应验证 JWT 或使用 OAuth 而非静态 token。

FastMCP · 从 OpenAPI 生成 MCP 工具 + 双层凭据 import os from fastmcp import FastMCP from fastmcp.server.auth.providers.jwt import StaticTokenVerifier # 上层：持有上游 API key，Agent 不可见 upstream = httpx2.AsyncClient( base_url="https://weather.example", headers={"X-API-Key": os.environ["UPSTREAM_API_KEY"]}) # 下层：MCP 端点自己的鉴权 mcp_auth = StaticTokenVerifier(tokens={ os.environ["MCP_API_KEY"]: {"client_id": "course-agent"}}) mcp = FastMCP.from_openapi( openapi_spec=spec, client=upstream, name="Weather MCP", auth=mcp_auth) mcp.run(transport="http", port=8001)
维度OpenAPI / HTTPMCP
共享名称、描述、JSON Schema 结构化输入
发现获取 OpenAPI 文档运行时调用 tools/list
调用HTTP 动词 + 路径 + 参数tools/call 走 MCP 传输
鉴权客户端直接鉴权 API客户端鉴权 MCP，上游鉴权独立
范围描述 HTTP 操作还支持 resources、prompts、扩展

一句话：OpenAPI 描述一个 Web API；MCP 标准化「AI 宿主如何发现和调用能力」。MCP 是 Agent 面向的接口层，不是调用 REST 的必需品。

多调用编排：串行 vs 并行

串行 · 逐个往返
  • 每步：生成(0.8s) + 工具(≈1s) + 生成 + 工具…
  • 3 个独立调用 ≈ 6.4 秒
  • 延迟随调用数线性增长
并行 · 一轮往返
  • 一次生成发出全部调用，等最慢的返回
  • 2 × 0.8 + max(1.2, 0.9, 1.1) ≈ 2.8 秒
  • 结果按 call_id 配对，乱序无妨
哪些可以并行？
✓ 安全并行

无依赖的独立调用

天气查询
读取今日日历
查询航班状态

互不依赖，可共享一次生成与等待。

✗ 必须串行

存在数据依赖

查客户 ID → 用 ID 取订单 → 退款

后一步需要前一步的输出，只能排队。

四层评测栈：失败发生在哪一层？

层级问题示例指标任务成功？典型失败
Selection 选择选对工具了吗？Precision / recall否缺失或多余调用
Arguments 参数参数值对了吗？AST / schema 匹配否字段或取值错误
Trajectory 轨迹顺序对吗？序列成功通常依赖关系错误
Task 任务目标达成了吗？端到端成功是貌似合理的错误答案

「任务成功」不代表「没有失败」——一个选错工具但最终正确回滚的 Agent 会在 Task 层得满分，却在 Selection 层暴露问题。评测必须分层定位。

质量还有运营维度

效率

Efficiency

延迟 · 调用数 · token · 成本。正确的 Agent 也可能慢到不可用。

可靠性

工具失败可能来自三层
模型

选错工具 · 参数错 · 忽略结果

Harness

解析失败 · 鉴权 · 校验 · ID 错配

Provider

超时 · 限流 · 执行错误

课程引用了 OpenRouter provider 的实测工具调用错误率：不同 provider 的错误率差异巨大——生产评测必须同时测量基准准确率与运营失败率。

思考题

Q1 · 工具选择
四类场景（当前信息 / 精确计算 / 私有状态 / 外部动作）中，哪一类最可能因为「模型幻觉」而选错工具？为什么？
查看参考思路
外部动作类风险最高：一次错误调用会产生真实副作用（下单、发信、部署）。因此这类工具应有最高级别的人类审批与权限控制。
Q2 · schema 约束的边界
XGrammar 保证工具调用的 JSON 合法。它不能保证什么？
查看参考思路
只保证形式：不保证语义正确（参数值是否符合业务逻辑）、不保证权限、不保证选对工具、不保证任务成功。这些需要评测与运行时校验。
Q3 · MCP 的价值
为什么说 MCP 的核心价值之一是「凭据代理」？直调 REST 时凭据会怎样暴露？
查看参考思路
直调时 API 密钥会出现在 Agent 的 shell 环境里，可被读取/复用；MCP 服务器持有上游密钥，Agent 只持 MCP 自己的凭据，模型两者都看不到——最小权限原则。
Q4 · 并行编排
0.8s 生成 + 三个 1.2/0.9/1.1s 的工具。并行比串行快多少？哪些情况不应该并行？
查看参考思路
串行 ≈ 6.4s，并行 ≈ 2.8s（2×0.8 + max）。有数据依赖的调用、共享可变状态的调用、或需要严格顺序的审计场景不应并行。
