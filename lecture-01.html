01

Agent 的标准定义

追溯自 Russell & Norvig《人工智能：一种现代方法》的经典定义：Agent 是一个通过传感器感知环境、通过执行器对环境采取行动的系统。这一定义同样适用于今天的 LLM Agent——只是「传感器」和「执行器」换成了软件接口。

感知 Sensors

观测何物

消息、文件内容、网页 DOM、屏幕截图、工具返回结果。Agent 看到的不是原始世界，而是模型化的观测。

行动 Actuators

改变何物

文本回复、编辑文件、执行 shell、调用 API、模拟鼠标键盘。每个动作都可能改变环境，从而改变下一步的观测。

02

从语言模型到 Agent

语言模型诞生之初只是「下一个 token 预测器」：给定前缀，续写最可能的文本。成为 Agent 的关键转变在于——把动作当作 token 来生成。一次工具调用、一条 shell 命令，都只是词汇表中的特殊符号被模型「写」出来。

模型在循环中

工具调用的消息协议

API 层把「工具调用」编码为一个特殊消息：模型返回 assistant.tool_calls，系统执行工具后回传 tool 角色的结果消息。这个「请求-响应」模式是几乎所有 Agent 框架的通用协议。

消息序列 · 一次工具调用往返 # 用户 user: 帮我查一下明天的天气 # 模型提议调用工具（动作即 token） assistant.tool_calls: [{"name": "get_weather", // 参数由模型生成，须符合 JSON Schema "arguments": {"city": "Beijing", "date": "tomorrow"}}] # 系统执行工具，结果作为新消息回传 tool: {"city": "Beijing", "temp_hi": 31, "temp_lo": 22} # 模型看到结果，继续生成最终回复 assistant: 北京明天多云，最高 31°C，最低 22°C。
💡 关键洞察
工具调用之所以可行，是因为模型已把「函数签名 + 调用约定」隐含地从训练数据中学会。框架层不需要任何新训练——只需在消息格式上做文章：告诉模型有哪些工具可用，剩下交给下一个 token 预测。
03

最小 ReAct 循环

ReAct（Reason + Act，Yao et al. 2022）是 Agent 最经典的范式：模型思考（reasoning）→ 行动（action）→ 观测（observation）→ 再思考。这一讲用 mini-swe-agent 展示了它的最小实现——核心只需要 20 行。

mini-swe-agent · 20 行最小 Agent 循环（Python） def run(user_request): # 初始化：系统提示 + 用户请求 messages = [system_prompt(), user_request] while True: # ① 查询模型 → 得到回复（可能是工具调用） reply = query(messages) # ② 执行动作（在沙箱 shell 中） obs = execute_actions(reply) # ③ 动作结果作为观测追加回上下文 messages = messages + reply + obs # ④ 模型认为任务完成 → 输出最终答案 if reply.is_final_answer(): return reply.content

💡 为什么「模型在循环中」足够强大
循环本身没有智能——智能全部来自模型。循环只负责三件事：让模型看到工具结果（观测）、把结果存回上下文（记忆）、在合适时机停止（终止条件）。这三点正是 Agent 工程的全部基础，后续每讲都在深化其中一环。
04

六项核心能力

本课程把「构建 Agent」拆成六项可独立评测、独立训练/工程化的能力（Neubig 等人的 AgentBench 框架）：

01

准确工具调用

模型能依 JSON Schema 生成合法调用，选对工具、填对参数。评测：ToolBench 等工具选择基准。

02

长上下文连贯性

循环数小时后仍能记得目标、不从上下文迷失。涉及注意力机制、记忆与压缩。

03

可定制性

Agent 能按要求改变自己的行为：遵循风格指南、学习新技能。技能系统与 prompt 工程。

04

复杂任务管理

面对可分解的长任务（如软件开发），能规划、拆解、按序执行。规划与任务分解。

05

环境理解

从观测中正确理解状态：读网页、看截图、查代码库，推断环境隐含信息（如 CSV 格式）。

06

安全

权限边界、沙箱隔离、防止提示注入、拒绝危险动作。不可模糊，必须显式设计。

这六项能力有两种获得途径，对应课程的两个主题词：

模型训练
  • 预训练（Pretraining）：海量文本，学会语言与世界知识
  • 中间训练（Mid-training）：注入代码、工具、长上下文数据
  • SFT：跟随指令、模仿高质量 Agent 轨迹
  • RL：用奖励信号优化工具使用与长程决策
Harness 工程
  • 提示词设计：怎么描述工具、怎么引导思考
  • 工具与环境：执行沙箱、API 封装
  • 记忆系统：上下文管理、技能存储
  • 控制流：循环、规划、重试、终止策略

真实系统几乎总是两者结合：模型能力有上限时用 harness 弥补，harness 拗不动时回到训练。工程与训练的分界线，是本课程反复出现的主题。

05

训练 vs Harness 工程

模型能力的完整训练流水线是一个三段链路。课程将其类比为「通用知识 → 领域技能 → 行为偏好」的逐步精炼：

LLM 训练流水线
预训练 Pretraining
数万亿 token · 语言 + 世界知识
中间训练 Mid-training
代码 / 工具 / 长上下文 数据混合
SFT
指令跟随 + 优质 Agent 轨迹模仿
RL / 偏好优化
奖励信号 · 工具使用 · 长程决策
⚠️ 工程视角
对 Agent 产品开发者，大部分能力差距不靠训练，而是靠 harness：把工具描述写清楚、把失败重试做成循环、把上下文压缩做可靠、把技能维护做成流程。训练是最后一公里，不是第一公里。

完整 Agent 系统栈

把一个生产级 Agent 从内到外展开，是七层系统——每一层都有独立的工程与评测问题：

🌍 环境 Environment

🎛️ Harness
循环控制 · 工具注册 · 记忆 · 规划 · 技能
🧠 推理 Inference
模型调用 · 缓存 · 并发 · 路由
🤖 模型 Model

📊 监控 Monitoring
轨迹记录 · 成本 · 失败分析

持续收集数据改善模型

注意监控与训练是横向贯穿的：每次运行产生轨迹，轨迹既用于调试，也用于后续 SFT/RL 的数据生产。这是 Agent 系统区别于普通 Web 服务的独特闭环。

💡 课程愿景示例

08

思考题

Q1 · 工具调用的本质
为什么「把动作当作 token 生成」是可行的？这对工具设计的启示是什么？
查看参考思路
因为模型在训练数据中见过大量 API/CLI 调用模式，函数签名只是条件续写。启示：工具名要描述性强、参数 schema 要自解释，模型理解越容易，调用越准确。
Q2 · 训练 vs Harness
假设你的 Agent 总是「选错工具」。你应该先去 SFT 还是先改 prompt？判断依据是什么？
查看参考思路
先做诊断：是模型不认识工具（改描述/加示例），还是工具本身命名混淆（改名），还是需要新数据（再考虑训练）。成本从低到高：prompt → 示例 → 训练。
Q3 · 系统设计
生产级 Agent 系统中「监控」层为什么和「训练」层形成闭环？
查看参考思路
每次运行都是数据生产：成功轨迹成为 SFT 正例，失败轨迹经人工修正后成为训练数据，训练后的模型再上线产生新轨迹——形成持续改进循环。
