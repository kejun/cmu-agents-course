03

经验的三类形态

Episode 情节

完整轨迹

每个观测和动作的完整 trace。当精确的产品、价格或序列还会再出现时有价值。

Fact 事实

单条断言

「这家店只在商品页显示价格」。当事实在未来任务中复发或可更新时有价值。

Skill 技能

可复用动作模式

「填搜索框 → 点搜索 → 打开结果」。当后续任务重复同一模式时有价值。

记忆 vs 技能

Memory 记忆

从 Agent 自身交互中保存下来的内容。

e.g. 之前买过的某个产品

Skill 技能

关于如何行动的可复用知识——代码、文本或两者兼有。

e.g. 某人写的发布检查清单；
Agent 从自己成功搜索中归纳出的技能

04

人工撰写技能：SKILL.md 与渐进披露

技能的两条创建路径

Skills as instructions 指令Skills as learning 学习
作者人或组织Agent 自己
来源既有专长 · 策略 · 文档自身的情节与结果
优势意图与来源已知擅长「必须被发现」的技能
主要负担专家时间来写和维护判断结果 · 验证 · 策展

什么是一个技能包？

python-review/ 技能包结构 python-review/ ├── SKILL.md # 必需：元数据 + 指令 ├── scripts/ # 可选：可执行代码 ├── references/ # 可选：文档 └── assets/ # 可选：模板、资源
SKILL.md = YAML 元数据 + Markdown 正文 --- name: python-review description: 当用户要求 "review Python code"、"check Python style"、 "lint Python" 或提到代码质量时使用本技能。 triggers: - python review - code review - lint python --- # Python 代码审查 按公司标准审查 Python 代码……

渐进披露（Progressive disclosure）：名称与描述先进入上下文；正文在 Agent 触发技能时才加载；捆绑文件在读取时才加载。不要把全部细节塞进系统提示。

渐进披露的具体流程

回合进入上下文的内容成本
1 · System Prompt技能索引：仅名称+描述≈3K tokens（Hermes 实测）
2 · skill_view()SKILL.md 正文（审查步骤）一次加载
3 · 跑脚本脚本输出：Black / Ruff 发现源码本身永不进入上下文
4 · skill_view(参考文件)docstring 规则等仅当模型要求时
💡 与 Hermes 一一对应
CMU 课程在这里引用的正是开源 Agent Hermes 的实现：系统提示里只有技能索引、skill_view 按需加载正文、技能可含脚本。你在本机看到的 skills 机制就是本讲的活例子。

从轨迹归纳技能

技能 = 任务的可复用片段

SEARCH FOR A PRODUCT · 归纳为参数化片段 # To find {query}, I will type it into the store's search box and submit. fill('element145', {query}) click('element147')
REPORT A PRICE RANGE · 复用搜索片段 + 新增收尾 # To get the price range for {query}, I will first search the store for it. fill('element145', {query}) click('element147') # The results list a price on each card. I will read the lowest and the highest. send_msg_to_user("{low} to {high}")

程序归纳的血脉

系统做法
Voyager (2023)在 Minecraft 归纳越来越复杂的动作序列函数，相互调用。
DreamCoder (2021)归纳能压缩「已解程序库」的函数；后续搜索复用它们。
Stitch (2023)快速符号压缩：找最能捕获语料共享结构的函数。
LAPS (2021)自然语言任务描述指导归纳哪些函数、如何搜索。
LILO (2024)LLM 写程序 → Stitch 压缩成函数 → LLM 命名与文档化每个函数。

在线归纳技能：AWM（Agent Workflow Memory）

归纳提示（节选） 给定一组网页导航任务，你的任务是提取其中共同的工作流。 每个任务包含一句自然语言指令和一系列求解动作。 找出多个任务间重复的动作子集，把每个提取为一个工作流。 每个工作流应是被反复复用的子例程，至少两步。 用描述性变量名表示非固定元素（输入文本、按钮字符串），如示例所示。 AWM · Wang et al., ICLR 2025
评估设置：成功任务在下一个任务到来前更新记忆
① 成功 → 归纳
→ 技能记忆库
② 后续任务 → 应用
→ 累计成功率评估
技能：search product / add to wish list / report price range
08

文本技能 vs 代码技能

Text + examples 文本
Task: Search for gaming accessories within a date range Action trajectory: click(1274) # Navigate to Video Games category fill(473, {search_terms}) # Enter search terms click(478) # Execute the search
  • + 灵活：是提示，模型解释并适应眼前页面
  • − 手动：Agent 仍逐个发出底层动作，复制+修改
Code 代码
def search_product(search_box_id: str, query: str): """Search for a product using the search box.""" click(search_box_id) fill(search_box_id, query) keyboard_press('Enter')
  • + 可作为工具 · 可测试（存之前先跑）
  • + 层次化（技能调用技能）· 高效（一次调用替代多步）
  • − 脆弱：页面一改就按老规矩硬来

归纳代码技能：ASI（COLM 2025）

从情节归纳出可执行技能 # 情节（NL query + Actions） Tell me the number of reviews our store received that mention the term "satisfied" click("Marketing") → click("All Reviews") → fill(757, "satisfied") → click("Search") # 归纳出的技能（few-shot 提示 LM） def open_marketing_reviews(): """Navigate to All Reviews under Marketing.""" click("Marketing") click("All Reviews") def search_reviews(search_box_id, search_button_id, search_term): """Search for reviews with a specific term.""" fill(search_box_id, search_term) click(search_button_id) # 新任务直接组合调用 open_marketing_reviews() search_reviews('757', '704', "satisfied") send_msg_to_user("2")
💡 谱系
Voyager（Minecraft 代码技能库）→ ASI 把它带到网页环境：定义函数、写 docstring、给示例，然后像工具一样被调用。

从失败中学习：ReasoningBank 案例

一次失败的情节 → 三条策略 # 情节（失败） "提供 Sony 蓝牙耳机的完整型号名称与价格区间" search "Bluetooth headphones Sony" → 5,578 条全店结果，每页 12 条 → 翻页 → 翻页 → … → 步数上限，什么都没发给用户 # 归纳出的策略 1 · 搜索词优化 —— 宽泛词把答案埋进几千条松散结果，浏览前先收紧 2 · 调整每页条数 —— 每页 12 条让每次"next"以很低覆盖率为代价花一步 3 · 使用现有过滤器 —— 侧边栏分类过滤器直接缩小列表，无需翻页

判官（Judge）准确率有多重要？

💡 模拟实验结论
把真实判官换成「以固定概率翻转标签」的模拟判官（从 oracle 到抛硬币）：性能依赖判官准确率，但在很宽的判官质量范围内性能都持续改善——不必追求完美判官，够好就行。
11

过度检索与记忆整合

⚠️ 过度检索（over-retrieval）
检索额外经验反而会让性能下降——ReasoningBank 在 WebArena shopping 的实测，SkillsBench 对人类策展技能也有同样的发现。原因：
① 部分经验本就无关（记忆本身的局限）；
② Agent 能条件化的容量有限。检索不是越多越好。

记忆整合（Consolidation）

TroVE：淘汰低频技能 # n = 已见样本数 # 使用次数 < ½·log₁₀(n) 的函数直接丢弃 if usage_count < 0.5 * math.log10(n): retire(skill) TroVE · Wang et al., ICML 2024

另一教训：「并非所有技能都有帮助」——一个技能帮助某类任务的同时可能伤害另一类任务。

决策人的努力有价值当…Agent 的努力有价值当…
Author / Induce技能或策略已经已知必须通过交互发现
Verify / Admit正确性是规范性的或高风险结果可执行且测试便宜

13

思考题

Q1 · 经验分类
下面三条，各应存为 Episode、Fact 还是 Skill？（a）「上次在 Target 买过 A 产品」；（b）「Target 的价格只在商品详情页显示」；（c）「在 Target 结账的完整操作序列」
查看参考思路
(a) 存为 Fact（买过什么产品）；(b) 存为 Fact（站点行为事实）；(c) 里「结账流程」若还会复用就归纳成 Skill，原始轨迹作为 Episode 保留用于精确回溯。原则：判断「还会不会再来」。
Q2 · 文本 vs 代码
网页 Agent 的代码技能 vs 文本技能各在什么场景下更优？为什么 SkillsBench 里 13/87 任务技能反而有害？
查看参考思路
结构高度重复、页面稳定 → 代码技能（可测试、可组合、高效）；页面多变、需要解释适应 → 文本技能。技能有害通常因为它挤掉了模型默认的好策略——技能不是免费的，要评估净收益。
Q3 · 跨站迁移
PolySkill 为什么能跨站？跟 ASI 直接归纳动作序列有什么区别？
查看参考思路
ASI 的技能逐字绑定低层动作（click 某 selector），换站即碎。PolySkill 把技能写成抽象方法的组合，每个网站只实现原语浏览器动作——组合层一次编写、全站复用。
Q4 · 奖励设计
为什么 SAGE 要把「任务 2 复用了技能」放进奖励，而不是只看任务 1 成功？
查看参考思路
归纳技能是有代价的（写函数、测试、入库）；任务 1 的即时奖励无法区分「靠运气成功」和「因为沉淀了可复用知识而成功」。只有把后续任务的复用作为奖励信号，归纳器才学到「保存值得的东西」。
